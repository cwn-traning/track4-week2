# guide-requirement · ฟังลูกค้า → User Story → FR/BR/NFR

ใช้คู่กับ **guide-oracle** เสมอ (ทุกอย่างในขั้นนี้คือแหล่ง [D])

## A. docs/01-USER-STORIES.md
(input เก็บที่ `docs/00-INTERVIEW.md` เสมอ)

**โครงไฟล์**
1. ตาราง "ผู้ให้ข้อมูล": ชื่อ/บทบาท | ข้อมูลสำคัญ (อายุ อาชีพ ยอดสะสม ฯลฯ)
2. User Story ทีละข้อ:
   ```
   ### US-01 · <ชื่อเรื่องสั้น>   [Must]
   ในฐานะ <บทบาท (ชื่อคน)> ฉันอยาก <สิ่งที่ทำ> เพื่อ <ประโยชน์>
   เกณฑ์ยอมรับ:
   - AC1: <ตรวจได้ มีตัวเลข/ข้อความชัด>
   - AC2: <กรณีขอบ เช่น ขอบพอดี vs เกิน 1>
   มาจาก: <คำพูดของใคร>
   ```
3. ตารางสรุป: รหัส | เรื่อง | ใครขอ | ความสำคัญ + นับ Must/Should/Could
4. **คำถามที่ยังไม่ชัด** Q1, Q2, … (สิ่งที่ลูกค้าไม่ได้บอก เช่น ราคา ระยะเวลาบริการ)

**กติกา**
- ครอบคลุม **ทุกเรื่องที่ทุกคนพูด** ไม่ตัดทิ้ง · 1 story = 1 ความต้องการ
- Must = ไม่มีแล้วธุรกิจใช้ไม่ได้/ผิดกฎ · Should = สำคัญแต่มีทางอ้อม · Could = ดีถ้ามี
- **ข้อขัดแย้งใน interview** (เช่น เจ้าของห้ามเก็บรูป แต่ลูกค้าอยากอัปโหลดรูป) → ห้ามเลือกเอง เขียน story ที่เคารพทั้งสองฝ่ายถ้าทำได้ แล้วตั้งเป็นคำถาม
- เกณฑ์ยอมรับที่ดีมี **กรณีขอบ** และตัวอย่างตัวเลขที่คำนวณได้
- ห้ามศัพท์โปรแกรม (database, API) ใน story

## B. docs/02-REQUIREMENTS.md

**3 ตาราง**

| ตาราง | คอลัมน์ |
|---|---|
| **FR** ระบบทำอะไรได้ | FR-xx \| ความต้องการ \| มาจาก US |
| **BR** กฎธุรกิจ (ต้องมีตัวเลข) | BR-xx \| กฎ \| ค่าขอบที่ต้องทดสอบ (ต่ำกว่า / ที่ขอบ / เกินขอบ) \| มาจาก US \| ⚠️ |
| **NFR** ดีแค่ไหน | NFR-xx \| ความต้องการ \| วิธีวัด (ตัวเลข/เครื่องมือ) \| มาจาก US |

**ต้องมี**
- **BR ลำดับการคิดเงิน** เมื่อมีส่วนลดหลายแบบ (ซ้อนได้ไหม คิดอะไรก่อน) — มักไม่มีใน story ตรง ๆ แต่เป็นจุดบั๊กบ่อย
- **NFR ด้านทดสอบได้** (เสมอ):
  - "AI"/ระบบแนะนำ ใช้กฎตายตัว: input เดิม → output เดิม
  - มีวิธีรีเซ็ตข้อมูลทดสอบกลับเป็น seed
  - ล็อก "วันนี้/เวลาปัจจุบัน" ของระบบได้
  - ทุกปุ่ม/ช่องกรอก/ผลลัพธ์/ข้อความ error มี test id
- NFR ตัวอย่างวิธีวัด: `scrollWidth ≤ 375` บนจอ 375px · หน้าแรกโหลด ≤ 3 วินาที · หน้าภาษาอื่นไม่มีอักษรไทย (ยกเว้นสัญลักษณ์เช่น ฿) · คำขอส่งรูปออกนอกเครื่อง = 0

**ท้ายไฟล์**
1. ตาราง coverage: US | FR | BR | ✅/❌ — ห้ามมี ❌
2. ตารางสมมติฐาน: ⚠️ | สมมติฐานที่ใช้ | โยง Q ไหนใน USER-STORIES
3. สรุป: ชนิด | จำนวน | ตัวอย่าง 1 ข้อ

## ไปต่อได้เมื่อ
- USER-STORIES มี Must อย่างน้อย 1 ข้อ และคำถามที่ยังไม่ชัด
- REQUIREMENTS ครบ 3 ตาราง · BR ทุกข้อมีค่าขอบ 3 ค่า · coverage ไม่มี ❌

# guide-testplan · module → ฟัง 3 ทาง → แผนทดสอบ → รีวิว

ใช้คู่กับ **guide-oracle** (โครงโฟลเดอร์ข้อ 1, qa.config.json ข้อ 2) · ขั้นนี้ **ห้ามแก้โค้ดเว็บ** · อ่านโค้ดได้ถ้าจำเป็น แต่ **ผลที่คาดหวังห้ามมาจากโค้ด** (โค้ด = [A])

## A. กำหนด module (ต้นขั้น /07 — ทำครั้งเดียว)
1. ร่างจาก `docs/02-REQUIREMENTS.md` (จัด FR/BR ตามเรื่อง) + เมนู/หน้าใน SPEC
2. แต่ละ module: `id` (2–5 ตัวพิมพ์ใหญ่ เช่น BOOK) · `folder` (kebab-case เช่น booking) · `title` ไทย · FR/BR ที่อยู่ใน module
3. ตรวจว่า **ทุก FR/BR อยู่ใน module ใด module หนึ่ง** · เรื่องข้ามระบบ (สิทธิ์, ภาษา, มือถือ) ทำเป็น module ของตัวเองได้ เช่น SEC, I18N, UX
4. **แสดงตาราง id | folder | title | FR | BR ให้ผู้ใช้ยืนยันก่อน** (ใช้ AskUserQuestion หรือถามในแชท) แก้ตามที่บอกจนผู้ใช้ OK
5. เขียน `playwright/e2e/qa.config.json` (baseURL/health/reset จาก SPEC, lockedNow จาก TEST-DATA) · ถ้าไฟล์มีอยู่แล้ว อ่านแล้วใช้ต่อ เปลี่ยน module เฉพาะเมื่อผู้ใช้ขอ

## B. ก่อนทุกการลองเว็บ
- อ่าน baseURL/health/reset จาก `qa.config.json` · เช็ก health · เรียก **reset ก่อนและหลัง** ทุกกลุ่มเคส (การสำรวจสร้างข้อมูลจริง)
- ใช้ Playwright MCP ในแท็บใหม่ · ภาพเก็บที่ `playwright/exploration/<module.folder>/<หน้า>-<ขั้น>.png`

## C. playwright/07-EXPLORATION.md (ลำดับตั้งใจ: คิดจากลูกค้าก่อน → อ่าน AI → เปิดเว็บ)
- **ขั้น 1 ฟังลูกค้า [D]** (ยังไม่เปิดเว็บ): "สิ่งที่ลูกค้าบอกว่าต้องเจอ" + ตัวเลขที่คำนวณเองไว้ก่อน แยกตาม module
- **ขั้น 2 ฟัง AI [A]**: SPEC/ASSETS อ้างว่ามีหน้า/ฟีเจอร์/กฎอะไร
- **ขั้น 3 ฟังเว็บ [O]**: กดทุกเมนู/ลิงก์ · งานหลักจนจบ 1 รอบด้วยผู้ใช้จาก TEST-DATA · สลับภาษา · มือถือ 390px · บัญชีพิเศษจาก SPEC ใช้ได้แต่จดว่าลูกค้าไม่ได้ให้

ต้นไฟล์: ตาราง module (คัดจาก qa.config) · ส่วน A–F **แยกหัวข้อย่อยตาม module** (`### BOOK · จองคิว`)

| ส่วน | เนื้อหา |
|---|---|
| A แผนผังเว็บ | module \| หน้า \| URL \| ไปจากไหน \| ต้อง login \| SPEC อ้างไหม |
| B ฟีเจอร์ | module \| ฟีเจอร์ \| หน้า \| ทำอะไรได้ \| input \| FR |
| C กฎ 3 ทาง | C.1 ฟอร์ม (ส่งเปล่า/ค่าผิด/ค่าขอบ + error ตรงตัวอักษร) · C.2 เงิน/ขีดจำกัด/สถานะ: กฎ(BR) \| ตัวอย่าง \| [D] \| [A] \| [O] \| ✅⚠️❌ |
| D ช่องว่าง 3 แบบ | ลูกค้าขอแต่ไม่มี · มีแต่ลูกค้าไม่ได้ขอ · AI อ้างแต่ใช้ไม่ได้ |
| E ความเสี่ยง | module \| ฟีเจอร์ \| ถ้าพัง \| P1/P2/P3 \| เหตุผล |
| F คำถาม | "ถามลูกค้า" (กฎไม่ชัด) / "ถามคนสร้าง" (ทำแบบนี้เพราะอะไร) |
| ยังไม่รู้ | อย่าเดา |

**ส่วน C ต้องลอง**: เงินทุกแบบ (คำนวณก่อน) · ช่วงวัน/เวลา/จำนวน · ชน/ซ้อน · **รีโหลดแล้วยังถูก** · **กดยืนยัน 2 ครั้งเร็ว ๆ แล้วนับผล** · logout แล้วเข้าหน้าสมาชิก/ใช้ cookie เดิม · ตัวเลขที่ต้องอัปเดตหลังรายการ (ทันที vs หลังรีโหลด) · ห้ามถือว่าหน้าจอถูก
P1 = เงินผิด รายการผิด/ซ้อน สิทธิ์/ข้อมูลส่วนตัวผิด · P2 = ฟีเจอร์สำคัญผิดแต่ยังใช้งานหลักได้ · P3 = แสดงผล/เกิดไม่บ่อย

## D. playwright/08-TEST-PLAN.md 8 หัวข้อ (ไฟล์เดียว แบ่งหัวข้อย่อยตาม module)
1. **ภาพรวม**: เป้าหมาย 1 ประโยค · ระบบ · เครื่องมือ · สิ่งที่ส่ง · ลำดับ oracle [D] > [R] > [A] > [O] · ตาราง module
2. **ขอบเขต**: ทุกฟีเจอร์ในส่วน B อยู่ฝั่ง ✅ / ❌ (มีเหตุผล) แยกตาม module · เบราว์เซอร์ · จอ · API · ตาราง "คำถาม | คำตอบที่ใช้" (ไม่แน่ใจให้ถามผู้ใช้)
3. **6 เทคนิค** พร้อมตัวอย่างจากระบบนี้: Happy path · Negative · Boundary · Equivalence partition · State · Security/API
4. **ระดับ** P1/P2/P3 ตามส่วน E + คำถามจัดระดับ 3 ข้อ (ตอบ "ใช่" ข้อแรกแล้วหยุด)
5. **Test cases** หัวข้อย่อยต่อ module:
   `ID (TC-<MOD>-01) | สิ่งที่ทดสอบ | FR/BR | เทคนิค | ระดับ | ข้อมูล (จาก TEST-DATA) | ผลที่คาดหวัง | จังหวะตรวจ | ที่มา | spec file`
   `spec file` = `tests/<folder>/<ชื่อ>.spec.ts` (หลาย TC อยู่ไฟล์เดียวได้)
   ต้องมีอย่างน้อย: flow หลักจนจบ (E2E) · ค่าขอบทุก BR สำคัญ · ชน/ซ้อน · กดซ้ำ · การหักยอด/สถานะเปลี่ยน · ช่วงวัน · เรียก API ที่ต้อง login โดยไม่ login · แก้ข้อมูลของคนอื่น · ข้อที่ ❌/⚠️ จากส่วน C
6. **Entry/Exit**: Entry = health ok · Exit = จาก `qa.config.exit` (P1 ผ่านทั้งหมด + ผ่านรวม ≥ passRate นับข้อปัดขึ้น, ไม่ได้รัน = ไม่ผ่าน) ตัดสินแยกทีละเบราว์เซอร์ · แสดงผลราย module ประกอบ · TC ที่ยิง API อย่างเดียวรันครั้งเดียวนับทุกเบราว์เซอร์
7. **ข้อมูลทดสอบ**: จาก TEST-DATA + ที่ตั้งเอง → ใช้กับ TC ไหน
8. **คุณภาพของแผน**: 8.1 "ถ้าเว็บพังแบบนี้ → TC ไหนล้ม → ทำไมจับได้ (oracle)" ≥ 6 แบบ ครอบเงิน/รายการ/สถานะ/สิทธิ์ · 8.2 จุดกำกวมจากส่วน F + สมมติฐานที่แผนใช้

**ลองกับเว็บจริง (`playwright/08-TEST-RUN-1.md`)**: reset ก่อนทุก TC · module | ID | ผลที่คาดหวัง | เว็บจริง | ตรงไหม · ไม่ตรง → ⚠️ + คิดว่าเว็บผิดหรือแผนเข้าใจผิด เพราะอะไร (**ห้ามแก้ expected**)
สรุป: module | TC | P1 | P2 | P3 · นับตามที่มาที่น่าเชื่อที่สุด [D] / [R] / [O-ยังไม่ยืนยัน]

> โปรเจกต์ใหญ่ (> 8 module หรือ > ~150 TC): แยกหัวข้อ 5 เป็น `playwright/plans/<folder>.md` แล้วให้ 08-TEST-PLAN.md เป็นสารบัญ (หัวข้อ 1–4, 6–8 ยังอยู่ที่ไฟล์หลัก)

## E. playwright/09-PLAN-REVIEW.md
- **Coverage matrix**: แถว = module/ฟีเจอร์ในขอบเขต · คอลัมน์ = 6 เทคนิค · ช่อง = TC ID · ควรมีแต่ว่าง ⚠️ · เติมจากรีวิว ✚
- **Traceability**: FR/BR | module | TC (BR ในขอบเขตต้อง ≥ 1) · FR/BR ที่ไม่อยู่ใน module ใดเลย = ❌
- นับ TC ตาม module / ระดับ / เทคนิค / ที่มา (ก่อน vs หลังแก้)
- ตรวจทีละข้อ: expected ตรวจได้ไหม · **ข้อมูลทำให้คำตอบผิดได้ตัวเลขต่างจากคำตอบถูกไหม** (oracle อ่อน) · บอกจังหวะตรวจไหม · ซ้ำไหม · TC อยู่ module ถูกไหม
- สรุป 3–5 ข้อที่ควรแก้ **แล้วแก้ใน 08-TEST-PLAN.md ให้เลย** (อัปเดตตัวเลขหัวข้อ 6) · เรื่องที่ต้องถามลูกค้า บอกผู้ใช้

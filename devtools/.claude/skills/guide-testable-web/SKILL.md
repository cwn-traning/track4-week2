# guide-testable-web · สร้างเว็บที่พิสูจน์ได้

ใช้คู่กับ **guide-oracle** · stack อ่านจากหัว DESIGN.md (ไม่ล็อก) · ด้านล่างเป็นหลักการ ตัวอย่างเป็น Next.js + PostgreSQL + Docker

## A. 6 สิ่งที่ทำให้ทดสอบได้ (บังคับทุก stack)

| # | สิ่งที่ต้องมี | ตัวอย่าง |
|---|---|---|
| 1 | **Reset** กลับเป็น seed | `POST /api/test/reset` เปิดเมื่อ env `ALLOW_TEST_RESET=1` เท่านั้น (production ต้องปิด) · ตอบ `{"ok":true}` เร็ว (< 1 วินาที) |
| 2 | **ล็อกเวลา** | reset รับ `{"now":"<ISO>"}` · ไม่ส่ง = ใช้วันล็อกใน TEST-DATA · ทุกกฎที่ใช้เวลาอ่านจากนาฬิกากลางตัวเดียว |
| 3 | **test id** | `data-testid` ทุกปุ่ม ช่องกรอก ผลลัพธ์ ข้อความ error · `<html data-ready="true">` เมื่อพร้อม |
| 4 | **Health** | `GET /api/health` → `{"ok":true,"db":true}` (db ต่อไม่ได้ = `db:false`) · ใช้เป็น healthcheck ของ container |
| 5 | **Seed = TEST-DATA ทุกค่า** | ห้ามเพิ่ม/เปลี่ยนเงียบ ๆ · ที่เพิ่มเองต้องจดใน SPEC เป็น ⚠️ |
| 6 | **กฎตายตัว** | "AI"/ระบบแนะนำไม่เรียก API ภายนอก · input เดิมได้ผลเดิม |

## B. แยกโครงสร้าง (ตัวอย่าง Docker)
- `app/db/` compose แยก: container `<app>-db` · volume · พอร์ต `5433:5432` (กันชน DB ในเครื่อง) · healthcheck `pg_isready` · `init/01-schema.sql` ตาม ERD · `init/02-seed.sql` ตาม `docs/04-TEST-DATA.md`
- `app/web/` compose แยก: container `<app>-web` พอร์ต 3000 · `DATABASE_URL` ชี้ `<app>-db:5432` (ไม่ใช่ 5433) · ทั้งคู่อยู่ network `<app>-net`
- healthcheck web ด้วย runtime ที่มีอยู่แล้ว (เช่น `node -e "fetch('http://127.0.0.1:3000/api/health')..."`) ไม่พึ่ง curl
- **ห้ามต่อ DB ตอน build** (หน้าที่อ่าน DB ต้อง dynamic) · เปิด db → รอ healthy → เปิด web
- Windows: ไม่มี `.sh` ที่ต้องรัน · `.gitattributes` บังคับ LF · คำสั่งใช้ใน PowerShell ได้ · ก่อนเปิดเช็กพอร์ตว่าง (ถ้าชน ถามผู้ใช้ก่อน stop)
- เงินใช้ NUMERIC/Decimal ไม่ใช้ float · ใช้ transaction + กันกดซ้ำ (idempotency / unique constraint) ในรายการที่สร้างข้อมูล

## C. เอกสารที่เว็บต้องส่ง (ใน `app/web/`)
- **`app/web/SPEC.md`** (= [A]): หน้าเว็บ + URL · กฎโยง FR/BR · `data-testid` ทุกตัว · ข้อความ error คำต่อคำ (ทุกภาษา) · API ทุกเส้น (method, body, status) · ผู้ใช้ seed · **สมมติฐานที่ผู้สร้างตั้งเอง** (⚠️ ต้องถามลูกค้า)
- **`ASSETS.md`** (ถ้ามีรูป): ไฟล์ | ใช้ที่หน้าไหน | สร้างด้วยอะไร

## D. รูปภาพ
ห้ามใช้รูปจากเน็ต/ลิขสิทธิ์คนอื่น · เก็บใน `public/assets/` · เช็ก `codex --version`:
มี Codex CLI → `codex exec` ใช้ image generation (รูปอยู่ใต้ `~/.codex/generated_images` คัดลอกมาแล้วย่อด้วย sharp) · ไม่มี/ล้มเหลว → วาด SVG/CSS เฉพาะรูปนั้น · ภาพคนเป็นภาพวาด ไม่ใช่คนจริง

## D2. Design Brief (ส่วนที่ตัดสินว่าเว็บสวยไหม — บังคับในขั้น 6 ของ BUILD-PROMPT)
คำว่า "ดีไซน์สวย ทันสมัย" อย่างเดียว = เว็บหน้าตา generic · ต้องเขียนเป็น **ค่าที่ตรวจได้** ครบ 9 หัวข้อ:
1. **ทิศทาง + token**: อารมณ์ 3 คำ + คำที่ห้าม · ตารางสี (hex + ใช้กับอะไร + คอนทราสต์) · ฟอนต์หัวข้อ/เนื้อหา (ไทยต้องรองรับ เช่น Mitr, Prompt, IBM Plex Sans Thai, Noto Sans Thai, Anuphan) · type scale · spacing scale · radius · เงา ≤ 2 ระดับ · ห้ามสีนอก token
2. **Layout**: container · gutter · breakpoint (mobile first 375) · grid ต่อขนาดจอ · header มือถือ/เดสก์ท็อป
3. **หน้าหลัก**: ตาราง หน้า | สิ่งแรกที่เห็น | โครงจากบนลงล่าง
4. **คอมโพเนนต์ + สถานะ**: hover / focus-visible / disabled (+เหตุผล) / loading (กันกดซ้ำ) · label ไม่ใช่ placeholder · empty / skeleton / error ทั้งหน้า · toast
5. **Motion**: ระยะเวลา · easing · ระยะเคลื่อน · `prefers-reduced-motion`
6. **เนื้อหา**: ภาษา · ไฟล์แปล · ห้าม lorem ipsum · โทน microcopy · รูปแบบราคา/เวลา
7. **Art direction ของรูป**: สไตล์ แสง โทน มุมกล้อง สัดส่วนต่อชนิดรูป · ทุกรูปเป็นชุดเดียวกัน · alt
8. **Accessibility**: คอนทราสต์ ≥ 4.5:1 · เป้าแตะ ≥ 44px · คีย์บอร์ด · heading
9. **Visual QA**: จับภาพทุกหน้า 375/768/1280 → ตรวจตามเช็กลิสต์ → แก้ → `DESIGN-QA.md` (ห้ามจบขั้น build ถ้ายังไม่ผ่าน)

### D3. ปรึกษาดีไซน์กับผู้ใช้ (ทำใน /05 ก่อนเขียน — ตามกติกา guide-oracle ข้อ 9)

**ขั้น 1 · วิเคราะห์จาก docs แล้วสรุปให้ผู้ใช้เห็น**
| ปัจจัย | อ่านจาก | ส่งผลต่อ |
|---|---|---|
| ประเภทธุรกิจ/บุคลิกแบรนด์ | 00-INTERVIEW · 01-USER-STORIES | อารมณ์ · สี · ฟอนต์หัวข้อ |
| ลูกค้าหลัก (อายุ ภาษา ความคุ้นเคยเทคโนโลยี) | ผู้ให้ข้อมูลใน 01 | ขนาดตัวอักษร · ความหนาแน่น · คำศัพท์ |
| อุปกรณ์/สถานการณ์ใช้งาน | US + NFR | mobile-first ไหม · ขนาดเป้าแตะ · ปุ่มลอย |
| งานหลัก 1–2 อย่าง | Must stories | สิ่งแรกที่เห็นในหน้าแรก |
| ข้อจำกัด | NFR · interview (เช่น ห้ามเก็บรูป, 3 ภาษา) | ฟอนต์ที่รองรับหลายภาษา · รูปภาพ |
| สิ่งที่ลูกค้าพูดถึงหน้าตาตรง ๆ | interview | ล็อกเป็นข้อบังคับ ไม่ต้องถาม |

**ขั้น 2 · ถามกลับ (AskUserQuestion รอบ 1, ≤ 4 ข้อ) — ตัวเลือกแรก = แนะนำ พร้อมเหตุผลจากขั้น 1**
1. **ทิศทางดีไซน์** — เสนอ 3 ทิศทางที่ต่างกันจริง แต่ละตัวมี `preview` (อารมณ์ 3 คำ · สี 4 ตัว hex · ฟอนต์หัวข้อ/เนื้อหา · ตัวอย่างหน้าแรกแบบ ASCII)
   ตัวอย่างสำหรับร้านกาแฟ: A อบอุ่น·ไม้·แสงเช้า (แนะนำ: ลูกค้าเป็นคนในย่าน มาซ้ำ) · B มินิมอล·ขาวดำ·specialty · C สนุก·สีสด·ภาพประกอบ
2. **มีแบรนด์เดิมไหม** — มีโลโก้/สีแล้ว (แนบ/บอก hex) · ยังไม่มี ให้ออกแบบตามทิศทางที่เลือก (แนะนำถ้า docs ไม่พูดถึง)
3. **อุปกรณ์หลัก** — มือถือก่อน (แนะนำถ้า US พูดถึง "สั่งจากมือถือ"/ลูกค้าเดินผ่าน) · คอมก่อน (ระบบหลังร้าน/องค์กร) · เท่ากัน
4. **ระดับลูกเล่น** — นุ่มนวล (แนะนำ: โหลดเร็ว ทดสอบนิ่ง) · เรียบสุด (ระบบภายใน) · เด่น (landing page การตลาด)

**ขั้น 3 · ถามรอบ 2 เฉพาะที่ยังไม่ชัด (ไม่บังคับ)**: เว็บอ้างอิงที่ชอบ/ไม่ชอบ · รูปภาพ (ภาพถ่ายสมจริง / ภาพประกอบ / ไม่มีรูป) · dark mode · ขนาดตัวอักษร (ถ้าลูกค้าสูงอายุ แนะนำ body 18px)

**ขั้น 4 · เสนอ token ให้ยืนยัน** — ตารางสี + ฟอนต์ + type scale จากทิศทางที่เลือก พร้อมคอนทราสต์ที่คำนวณจริง · ผู้ใช้ OK แล้วค่อยเขียน BUILD-PROMPT

**ขั้น 5 · บันทึก** ต้น `docs/05-BUILD-PROMPT.md` ส่วน "การตัดสินใจด้านดีไซน์": เรื่อง | เลือก | แนะนำไว้ | เหตุผล

> ห้ามเสนอทิศทางที่ต่างกันแค่สี (ต้องต่างทั้งอารมณ์ ฟอนต์ ความหนาแน่น รูปภาพ) · ห้ามเสนอสิ่งที่ขัด NFR (เช่น ฟอนต์ที่ไม่มีภาษาจีนในเว็บ 3 ภาษา)

**ตัวอย่างเต็ม (ระดับความละเอียดที่ต้องการ):** [examples/05-BUILD-PROMPT.example.md](examples/05-BUILD-PROMPT.example.md)

## E. Template `docs/05-BUILD-PROMPT.md` (~150–250 บรรทัด, มีเลขขั้น · ขั้น 6 Design Brief ห้ามย่อ)
```
0. อ่านก่อนลงมือ: docs/02-REQUIREMENTS · docs/03-DESIGN · docs/04-TEST-DATA · ถ้าขัดกัน TEST-DATA > REQUIREMENTS > DESIGN · ไม่แน่ใจให้ถาม
1. Stack + โครงโฟลเดอร์ (จาก docs/03-DESIGN.md) · โค้ดอยู่ใน app/db/ และ app/web/ เท่านั้น ห้ามเขียนลง docs/ หรือ playwright/
2. ฐานข้อมูล: schema ตาม ERD + seed ตาม TEST-DATA ทุกค่า
3. Backend/API + กฎธุรกิจทุก BR (โยงรหัส)
4. Container/การรัน + healthcheck + พอร์ต + network
5. รูปภาพ (ข้อ D)
6. Design Brief ครบ 9 หัวข้อ (ส่วน D2) + Visual QA
7. ฟีเจอร์ครบทุก FR + หน้า admin ถ้ากฎต้องให้คนกด (เช่น "ใช้บริการเสร็จ")
8. ทดสอบได้ (ข้อ A ครบ 6 ข้อ)
9. เอกสาร SPEC.md / ASSETS.md
10. ตรวจตัวเอง: สคริปต์ยิง API ตามตารางค่าขอบ E-xx → รายงาน "ผ่าน X/Y" (= คำอ้าง [A] ยังไม่ใช่การพิสูจน์)
11. เปิดระบบ: db → web → /api/health → เปิดหน้าเว็บให้ผู้ใช้ดู · ขั้นไหนไม่ผ่านให้หยุดแล้วบอกสาเหตุ · สรุปเป็นตาราง
```
ท้าย BUILD-PROMPT: ตาราง ขั้น | FR/BR ที่ครอบคลุม (ต้องครบทุก FR/BR)

> **ไม่มี BUG_MODE / การฝังบั๊ก** — workflow นี้ใช้กับงานจริง

## ไปต่อได้เมื่อ (หลัง build)
container ทั้งหมด healthy · `/api/health` ok · reset ใช้ได้ · มี SPEC.md · เปิดหน้าเว็บได้

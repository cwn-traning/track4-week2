# guide-testdata · ข้อมูลที่ลูกค้ายืนยัน (TEST-DATA.md)

ไฟล์: `docs/04-TEST-DATA.md` · ใช้คู่กับ **guide-oracle** · ไฟล์นี้ส่งให้ลูกค้าตรวจ เมื่อยืนยันแล้ว = **[D]** · เว็บต้อง seed ตามไฟล์นี้ **ทุกค่า**

## หมวดที่ต้องมี (ทุกตารางมีคอลัมน์ "มาจาก BR/US ไหน")

1. **วันเวลาล็อก** 1 ค่า + เหตุผล — เลือกให้ค่าขอบเวลาเกิดเองโดยไม่ต้องสร้างข้อมูลพิเศษ (เช่น ล็อก 10:00 → นัดพรุ่งนี้ 10:00 อยู่ที่ขอบ 24 ชม.พอดี)
2. **ผู้ใช้ตัวอย่าง** ≥ 4 คน: อีเมล | รหัสผ่าน | ชื่อ | ข้อมูลที่กฎใช้ (ยอดสะสม ระดับ แต้ม วันเกิด สิทธิ์ ฯลฯ)
   ต้องครอบ: คนที่ interview พูดถึงด้วยตัวเลขจริง · คนที่อยู่ **ขอบระดับ** (ต่ำกว่า 1 / ที่ขอบพอดี) · คนที่ใช้สิทธิ์ไปแล้ว · สมาชิกใหม่ · คนที่แต้ม/ยอดพอแลก
   รวมบัญชี admin/เจ้าของ ถ้าระบบต้องมี (ติด ⚠️ ถ้าลูกค้าไม่ได้ให้)
3. **Master data**: สินค้า/บริการ (ชื่อ | เวลา | ราคา | รายละเอียด) · แพ็กเกจ · ทรัพยากร (พนักงาน ห้อง) ที่มีพอทดสอบกลุ่มใหญ่สุด · ค่าระยะ/ระดับที่เป็นขอบ (เช่น 5.0 / 5.1 / 15.0 / 15.1)
4. **ข้อมูลตั้งต้น**: รายการที่มีอยู่แล้ว (ไว้ทดสอบชน/ซ้อน) · ของที่ยังใช้ได้ vs หมดอายุแล้ว
5. **ตารางค่าขอบ** E01, E02, … รวมจาก **BR ทุกข้อ**:
   `# | BR | เคส | input | ผลที่ถูก (วิธีคิด) | ทดสอบทาง (UI / API / unit test)`
   - เงินแสดงวิธีคิดเต็ม เช่น `฿4,000 − 10% = ฿3,600 − ฿100 = ฿3,500 + ฿300 = ฿3,800`
   - ปัดเศษระบุชัด เช่น `ปัดขึ้น(5 ÷ 4) = 2 คัน`
   - ค่าขอบที่ทดสอบผ่านหน้าเว็บไม่ได้ (ชนกฎอื่น เช่น วันในอดีต) → "unit test"
6. **ค่าที่ลูกค้ายังไม่ยืนยัน** T1, T2, … : ⚠️ | สมมติฐานที่ใช้ | กระทบเคสไหน

## ตรวจตัวเอง
- ตัวเลขในข้อมูลขัดกันเองไหม (เช่น ซื้อคอร์ส ฿15,000 แต่ยอดสะสม ฿12,400 → ถามว่านับเข้ายอดไหม) → ⚠️
- BR ทุกข้อมีแถวใน E-table (นับ "ครอบ BR X/Y")
- ข้อมูลทำให้ "คำตอบผิด" ต่างจาก "คำตอบถูก" ได้ชัดไหม

## สรุปท้าย
ตาราง หมวด | จำนวนแถว

## ไปต่อได้เมื่อ
มีวันล็อก ผู้ใช้ครอบขอบ และตารางค่าขอบครบทุก BR พร้อมวิธีคิด
